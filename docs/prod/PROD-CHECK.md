# Прод-проверки PokeMatrix (`tools/prod-check`)

Набор end-to-end проверок против **живого** прода `https://pokematrix.onrender.com`.
Гоняет настоящий Telegram-логин (initData подписывается реальным токеном прод-бота),
настоящие сокеты и настоящую БД — то есть проверяет ровно тот путь, которым ходит
игрок в Mini App.

Тестовые аккаунты стабильны: **777900101..107**. Боевые аккаунты игроков не
трогаются.

---

## 1. Как запускать

Токен прод-бота **не хранится в репозитории** — только через окружение.

```powershell
cd <repo>
$env:PROD_BOT_TOKEN = '<токен прод-бота>'
$env:PROD_BASE      = 'https://pokematrix.onrender.com'   # необязательно, это дефолт

# 0) дождаться, пока прод оживёт (ждёт 200 + {"status":"ok","db":true})
node tools/prod-check/wait-health.mjs --timeout-min 75 --interval-sec 20 --request-timeout-sec 15 --quiet

# 1) полный прогон, лог в файл
node tools/prod-check/run.mjs 2>&1 | Tee-Object -FilePath tools/prod-check/.state/prod-run.log
```

Точечно — один набор:

```powershell
node tools/prod-check/run.mjs infra    # HF1, V1, SJ1, CH1, LB1 — быстрая разведка
node tools/prod-check/run.mjs pvp      # PC1..PC21
node tools/prod-check/run.mjs trade    # TC1..TC15
node tools/prod-check/run.mjs arena    # TA1..TA9
```

Полезные переменные:

| Переменная | Смысл |
|---|---|
| `PROD_BOT_TOKEN` | **обязательна**, подпись тестовых initData |
| `PROD_BASE` | база, по умолчанию `https://pokematrix.onrender.com` |
| `PROD_API_TIMEOUT_MS` | таймаут одного HTTP-запроса, по умолчанию `20000`. Пока прод лежит, удобно ставить `3000`, чтобы разведка была быстрой |

Коды выхода: `0` — все проверки зелёные, `1` — есть красные, `2` — нет токена /
неизвестный набор.

`run.mjs` делает паузу 2 с между наборами: у сервера два общих скользящих лимита
по IP — auth `30/мин` (на каждый логин уходит 2 запроса: `/auth/tg` + `/auth/register`)
и `/api/save` `60/мин` (считает и GET, и POST). Два полных прогона в одну минуту
поймают `429`; при 429 нужно разнести прогоны по времени, а не «чинить» чек.

Прогон **пишет** в прод (это его смысл), но только в тестовые аккаунты:

- **CH1 добавляет одно сообщение в общий прод-чат** с маркером `pc-check-…` — его видно игрокам, публичного API удаления нет. Если чат важен, сообщение нужно убирать через админку.

## 4. Известные ограничения (не чинились намеренно)

1. **Счётчики в шапках.** До правки `run.mjs` обещал «38 проверок», а `lib.mjs`
   писал про юзеров `..105`. Реально проверок 50 (с учётом infra), юзеры `..107`.
   Счётчики исправлены, поведение не менялось.
2. **`testSave(over)` накладывает `over` на внешнюю обёртку**, а не на `saveData`.
   Из-за этого запасная ветка в `trade.mjs` (`if (r.status !== 200)`) отправляла
   дефолтный сейв вместо собранного и молча теряла кастомную команду/инвентарь.
   Исправлено: теперь запасная ветка шлёт тот же `sd` без `saveVersion`.
   `arena.mjs:28` этой ошибки не содержал.
3. **PC14 завязан на `saveVersion > 0`.** Чек шлёт `saveVersion - 1` и ждёт `409`,
   но сервер (`server/src/routes/save.ts:126-131`) отдаёт `409` только при
   `clientVersion > 0`. У стабильных тестовых юзеров версия давно больше 1, так
   что чек честный; на «свежем» аккаунте с версией 1 он бы ложно упал. Продукт
   не менялся — это осознанное поведение оптимистичной блокировки.
4. **TC5 проверяет уже не то, что написано в его названии.** `normalizeOffers`
   (`server/src/socket/trade.ts:92-100`) больше не сверяет id со списком
   `VALID_ITEM_IDS` (список отставал от игры и отбивал легальные предметы).
   Поэтому `hackedItem` отклоняется как «нет в инвентаре», а не как «неизвестный
   id». Чек зелёный и защиту от подделки проверяет (владение), но формулировка
   устарела. Название не менялось, чтобы не ломать историю id.
5. **Локальный dry-run невозможен.** В окружении нет локального Postgres/Docker,
   а Neon-квота egress общая для аккаунта — сервер не поднять. Поэтому логика
   набора выверялась статически по `server/src` **и** по реально задеплоенному
   `server/dist`, плюс проверялись CLI-пути и сетевые таймауты.
6. **`GET /api/chat/messages` отдаёт ПЕРВЫЕ 50 сообщений** (сортировка по `id`
   по возрастанию, `limit 50`), а не последние. Поэтому CH1 читает через
   `?since=` и, если там пусто, дополнительно дочитывает полный список — иначе
   на живом проде свежее сообщение просто не попало бы в ответ и чек ложно упал.
7. **Холодный старт Render Free.** Первый запрос после пробуждения инстанса
   может не уложиться в таймаут (30–60 с). В `api()` добавлен **один** повтор,
   и только для `GET`: `POST` повторять нельзя — запрос мог уже примениться,
   дубль дал бы лишнее сообщение в чате или лишний инкремент `saveVersion`.
   Поэтому `network error после 2 попыт.: timeout …` в логе — это холодный
   старт/недоступность (окружение), а не баг продукта. `429` — это лимиты
   (auth 30/мин на `tg`+`register`+`refresh`, save 60/мин с GET'ами): повторить
   набор через 60 с, а не «чинить» чек.
8. **CH1 оставляет след в общем прод-чате.** Проверка реально пишет в глобальный
   чат — по одному сообщению `pc-check-…` за прогон (на момент отчёта их 3:
   standalone infra + полный прогон + контрольный повтор). Публичного API
   удаления нет — это осознанная плата за проверку «чат работает». При
   необходимости чистится через админку.
9. **Спутники прогона пишут в БД прода.** Помимо сейвов тестовых юзеров,
   прогон создаёт строки `refresh_tokens` (по одной на логин, `refresh` помечает
   старую использованной), строки рейтинга боя и статистики арены. Всё — только
   на аккаунтах `777900101..107`.

## 5. Разбор провала: баг кода или окружение

| Симптом | Вероятная причина |
|---|---|
| `HTTP 0 network error: timeout …` у всех проверок сразу | служба не отвечает (Render спит / падает / БД недоступна). Сначала `wait-health.mjs`, и только потом разбор |
| `HTTP 503 {"status":"warming"}` | идут миграции при холодном старте — подождать |
| `HTTP 503 {"status":"degraded","db":false}` | `/api/health` не смог сделать `SELECT 1`: БД/квота/сеть до Neon. Это окружение, не игра |
| Все `PC*`/`TC*`/`TA*` красные, `HF1` зелёный | почти всегда `BOT_TOKEN` на Render не совпадает с `PROD_BOT_TOKEN` → `401 Invalid initData signature`. Сверить env на Render |
| `HTTP 429` | упёрлись в rate limit (auth 30/мин или save 60/мин). Разнести прогоны, не считать багом |
| `V1` красный (`commit != 12 hex`) | сервис запущен не на Render (`RENDER_GIT_COMMIT` не задан → `dev`), либо деплой сломан |
| `HF1` зелёный, но `TA8`/`LB1` пустые `entries` | пустая БД (после wipe) — не баг кода |
| Один-два чека красные при зелёном остальном | смотреть тело ответа в логе: это либо реальный баг продукта (тогда file:line в `server/src`), либо дрейф ожиданий чека |
